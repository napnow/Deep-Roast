# 多图图生图双模式设计

## 目标

让图生图支持两种明确的多图任务，而不是把多张图片默认合成一张：

1. 逐图修改：每张上传图片可以有自己的修改指令，分别生成结果。
2. 参考图修改：指定一张目标图，使用一张或多张参考图指导目标图的风格、构图或视觉元素。

第一版使用结构化界面表达任务，不自动解析“第一张修改成……第二张修改成……”等自然语言编号指令。这样可以保证目标图、参考图和积分数量明确；自然语言解析保留为后续扩展。

## 范围与约束

- 最多保留现有的 5 张上传图片限制。
- 保留单图编辑、批量变体、积分扣除、历史记录和失败重试能力。
- 逐图修改模式兼容现有可用图像模型：每个任务只向上游发送一张目标图。
- 参考图修改模式第一版只对 `gpt-image-2` 开放。当前服务器的 GPT Image 代理支持 JSON 数组和 multipart 多图请求；其它模型在能力未确认时返回可理解的切换模型提示。
- 不新增数据库表或迁移；任务关系仅存在于请求、响应和当前图片历史记录中。
- 不改变已有旧请求的语义：旧的 `{ image, prompt, count }` 请求继续按现有逐图生成逻辑兼容处理。

## 用户界面

### 模式选择

在图生图面板增加“处理方式”选择：

- “分别修改”：默认模式。
- “参考修改”：目标图按照其它参考图进行修改。

### 分别修改

- 顶部保留一个统一指令输入框，作为所有图片的默认指令。
- 每个缩略图下增加可选的“本图指令”输入框。
- 实际任务指令优先使用本图指令；为空时回落统一指令；统一指令和本图指令都为空时使用现有默认文案“生成这张图的变体”。
- 每张图对应一个独立任务，结果按上传顺序返回。

示例：

```text
图片 1 本图指令：改成赛博朋克风格
图片 2 本图指令：改成水彩插画风格
```

### 参考修改

- 每张缩略图提供“设为目标图”操作；同一时间只能有一张目标图。
- 其它图片可以勾选为参考图；至少需要一张目标图，参考图可为一张或多张。
- 使用一个统一指令输入框，例如“按照参考图的色彩和构图修改目标图”。
- 目标图不能同时作为自己的参考图。
- 生成前展示本次预计积分：参考模式只按输出数量计费，不按参考图片数量重复计费。

## 请求接口与任务模型

在服务层引入内部规范化任务类型：

```ts
type ImageEditTask =
  | {
      mode: "per-image";
      targetImage: string;
      prompt: string;
      targetIndex: number;
    }
  | {
      mode: "reference";
      targetImage: string;
      referenceImages: string[];
      prompt: string;
      targetIndex: number;
    };
```

`POST /api/image-edit` 和 `POST /api/image-edit/batch` 接受新结构，同时兼容旧结构：

```ts
type ImageEditRequest = {
  mode?: "per-image" | "reference";
  image?: string | string[];
  prompt?: string;
  items?: Array<{ image: string; prompt?: string; targetIndex?: number }>;
  targetImage?: string;
  referenceImages?: string[];
  model?: string;
  size?: string;
  count?: number;
};
```

规范化规则：

- 新的 `mode: "per-image"` 使用 `items` 生成独立任务。
- 新的 `mode: "reference"` 使用 `targetImage` 和 `referenceImages` 生成一个参考图任务。
- 没有 `mode` 的旧请求继续把 `image` 中的每张图片规范化为一个 `per-image` 任务，共用 `prompt`。
- 所有图片、任务数量和提示词长度沿用现有上限校验；空图片、空任务和自引用都返回 400。

响应继续保留 `images`, `total`, `succeeded`, `failed`, `lastError` 字段，并给每个生成结果增加任务关联字段：

```ts
{
  images: Array<{
    id: string;
    prompt: string;
    model: string;
    imageUrl: string;
    thumbUrl?: string;
    size: string;
    taskIndex: number;
    targetIndex: number;
  }>;
  total: number;
  succeeded: number;
  failed: number;
  lastError: string | null;
}
```

## 服务端流程

1. 路由完成登录、限流和 JSON 读取。
2. 图像服务将新旧请求统一规范化成 `ImageEditTask[]`。
3. 逐图任务逐个调用现有 `editImage`；每次上游只携带目标图片。
4. 参考图任务调用一次上游编辑接口，发送 `[targetImage, ...referenceImages]`；目标图始终位于第一张。
5. 对批量 `count`，按任务顺序串行生成，避免同时打爆上游配额。
6. 每成功落库一张结果，按一张图扣除一次积分；失败任务不扣积分。
7. 返回结果时保留 `taskIndex` 和 `targetIndex`，前端按任务关联结果并入历史。

### 上游代理请求

对于 `gpt-image-2`，服务层把多图作为图片数组传给配置的 `GPT_IMAGE_BASE_URL` `/images/edits` 接口。代理已经支持 `image`/`images` 数组及重复的 `image[]` multipart 字段，因此不需要更换代理或增加数据库配置。

对于不支持多图的模型，参考模式在发起上游请求前直接返回 400，提示用户切换到 GPT Image 2；逐图模式仍可继续使用这些模型。

## 积分与限流

- 逐图模式总成本为：`任务数量 × count × 单张图片积分`。
- 参考模式总成本为：`count × 单张图片积分`，参考图只提供输入，不额外计费。
- 保持现有的单图和批量接口限流；多任务请求在服务端统一预校验总积分。
- 预校验不足时不发起任何上游请求。
- 生成中单个任务失败时继续处理后续任务，响应中返回成功/失败计数和最后一个错误。

## 错误处理

- 前端在目标图、参考图或有效指令缺失时阻止提交，并显示具体提示。
- 服务端对非法模式、空数组、超过 5 张图片、目标图自引用和不支持参考模式的模型返回 400。
- 积分不足继续使用现有 `INSUFFICIENT_CREDITS` 错误，前端打开积分弹窗。
- 上游错误按任务记录，批量任务不会因单张失败而丢弃已经成功的结果。
- 保持现有浏览器取消行为；取消请求不会伪造成功结果，服务端已完成的任务仍按真实结果处理。

## 测试计划

测试先于实现，覆盖以下行为：

1. 任务规范化：旧请求、多图逐图请求、单个参考任务、空输入、自引用。
2. 积分计划：逐图按任务数量计费，参考模式不按参考图数量重复计费。
3. 上游请求：逐图只发送目标图；参考模式发送目标图在第一位且包含参考图数组。
4. 模型能力：参考模式拒绝非 `gpt-image-2`，逐图模式允许其它已配置模型。
5. 路由响应：结果保留 `taskIndex`、`targetIndex`，部分失败返回成功/失败计数。
6. 前端交互：模式切换、目标图选择、参考图选择、逐图指令回落和预计积分显示。
7. 回归：现有图生图、批量图生图、积分不足和历史记录测试继续通过。

## 非目标

- 第一版不自动解析自然语言中的“第一张/第二张”关系。
- 第一版不把多张目标图合成为一张海报。
- 第一版不修改 chatgpt2api 或 grok2api 容器代码。
- 第一版不新增异步任务队列；任务仍由现有请求链路串行完成。
