# 被邀请人奖励积分设计

## 背景

当前邀请机制允许管理员配置邀请人成功邀请后的奖励积分，但新用户无论是否通过邀请链接注册，都只获得固定的 50 积分注册赠送。管理员需要在现有“用户邀请”设置区域继续管理邀请人奖励，同时增加被邀请人的额外奖励配置。

## 目标

- 保留新用户注册时固定赠送的 50 积分。
- 为被邀请人增加一笔独立、可配置的额外积分奖励，默认 50 积分。
- 在管理员面板的现有“用户邀请”区域同时修改邀请人奖励和被邀请人奖励。
- 只有后续通过有效邀请关系完成的注册使用最新配置，历史奖励不追溯修改。
- 保存双方实际发放金额，保证邀请记录可审计。

## 非目标

- 不改变无邀请码注册用户获得的 50 积分。
- 不补发历史被邀请人的额外积分。
- 不改变邀请码、旧邀请码兼容、邀请开关和邀请人奖励的既有规则。
- 不增加新的管理员页面或新的权限模型。

## 用户界面

在 `AdminSiteSettingsCard` 的“用户邀请”区保留现有开关，并将奖励设置调整为两个输入项：

1. “邀请人奖励积分”：沿用现有 `invitationReward` 配置。
2. “被邀请人额外奖励积分”：新增 `invitationInviteeReward` 配置，默认显示 50。

两个输入项使用同一个“保存奖励”按钮提交，避免只保存其中一项造成管理员误判。输入必须是非负整数；保存成功提示“邀请奖励已保存，仅影响后续注册”。

邀请记录表增加被邀请人奖励展示：每条记录分别显示邀请人奖励和被邀请人额外奖励。历史记录的新字段为 0，因此不会把新规则错误地应用到旧数据。统计区域保留现有 `totalReward` 字段作为邀请人累计奖励，并新增 `totalInviteeReward` 展示被邀请人累计额外奖励，避免破坏现有 API 消费方。

## 数据模型与迁移

新增迁移 `drizzle/0014_invitee_invitation_reward.sql`：

- `site_settings.invitation_invitee_reward integer not null default 50`。
- `site_settings` 增加非负检查约束。
- `user_invitations.invitee_reward_amount integer not null default 0`。

`src/db/schema.ts` 同步增加上述字段。历史 `user_invitations` 记录填充为 0，表示部署前没有实际发放被邀请人额外奖励；迁移不修改任何用户积分余额。

新增积分流水类型 `invitee_reward`，用于区分被邀请人的额外奖励与既有 `signup_bonus`。`signup_bonus` 仍固定为 50，新增奖励单独写入一笔流水。

## API 与服务边界

- `GET /api/admin/site-settings` 返回 `invitationInviteeReward`。
- `PUT /api/admin/site-settings` 接受 `invitationInviteeReward`，与 `invitationEnabled`、`invitationReward` 一起由 `parseInvitationSettingsPatch` 完整校验后再更新。
- `site-settings` 服务将该字段映射为数字，并保持默认值 50。
- `listAdminInvitations` 返回每条记录的 `inviteeRewardAmount`，并新增 `stats.totalInviteeReward`；现有 `stats.totalReward` 保持邀请人奖励含义。
- 邀请奖励策略继续以有效、启用中的普通用户邀请人为前提；被邀请人奖励只在同一有效邀请关系成立时计算。

## 注册数据流

注册事务执行顺序保持原有结构：

1. 读取邀请开关、邀请人奖励和被邀请人奖励配置。
2. 验证邀请码对应的邀请人仍是启用中的普通用户。
3. 创建新用户，并写入固定 50 积分 `signup_bonus`。
4. 计算邀请人奖励和被邀请人额外奖励。
5. 更新邀请人余额并写入邀请人 `invite_reward` 流水。
6. 更新被邀请人余额并写入被邀请人 `invitee_reward` 流水。
7. 写入 `user_invitations`，分别保存 `rewardAmount` 和 `inviteeRewardAmount`。

所有步骤在同一个数据库事务中完成：任一方奖励失败时整个注册回滚，不会出现只给一方发放的半成功状态。若被邀请人奖励配置为 0，则不写入 0 金额流水，但邀请记录保存 0；被邀请人的固定 50 积分仍照常发放。

邀请功能关闭、没有邀请码或邀请码无效时，不发放额外被邀请人奖励；无效邀请码的既有错误行为保持不变。

## 校验与错误处理

- 两个奖励配置都必须是非负整数，拒绝负数、小数和非数字字符串。
- 配置校验在任何数据库更新前完成，避免开关已更新而奖励值更新失败。
- 注册奖励沿用当前邀请码有效性、邀请人状态和事务错误处理。
- 历史记录缺少新字段时按数据库默认值 0 返回。

## 测试与验收

新增或更新以下测试：

- 设置输入解析：同时解析两个奖励；拒绝任一奖励的负数、小数和非法字符串。
- 邀请策略：验证被邀请人额外奖励仅在启用且邀请关系有效时返回配置值，允许 0。
- 迁移契约：验证新列、默认值、非负检查和历史记录兼容迁移存在。
- 邀请记录查询：验证被邀请人奖励字段和累计统计字段映射。
- 全量验证：`npm test`、`npx tsc --noEmit`、相关 ESLint，以及 `npm run build`。

## 兼容性与部署

- 现有 `invitationReward` API 字段和 `stats.totalReward` 保持不变。
- 新设置默认 50，部署后新邀请用户会在原有注册 50 积分之外获得额外 50 积分。
- 旧邀请记录只显示实际历史奖励；不会因为迁移而补发积分。
- 迁移必须先于使用新字段的应用代码部署，生产部署后检查数据库迁移、构建、服务状态和未登录接口的既有鉴权行为。
