# 邀请机制设计

## 目标

为深焙增加可配置的用户邀请机制：普通用户拥有固定邀请链接，其他人通过链接完成注册后，邀请人立即获得管理员配置的积分奖励。管理员可以开启/关闭邀请功能、修改后续奖励积分，并查看邀请关系和奖励统计。

## 已确认规则

- 默认每次成功邀请奖励 200 积分。
- 被邀请人完成注册后立即发奖，不等待登录、签到或首次使用。
- 每个普通用户拥有一个固定、唯一、不可更换的随机邀请码。
- 管理员只负责管理，不生成邀请码、不参与邀请奖励。
- 邀请功能关闭时，普通注册仍可用；邀请参数被忽略，不建立关系、不发奖励。
- 修改奖励积分只影响之后的注册邀请，历史奖励不追溯调整。
- 奖励积分允许设置为 0；仍记录邀请关系，但不增加积分。
- 普通用户可以查看自己的链接、成功邀请人数、累计奖励、被邀请用户名和注册时间。
- 封禁或删除账号不追回已发积分；邀请历史通过用户名快照保留。
- 被封禁的普通用户不再产生新的有效邀请奖励。
- 继续使用现有的生产环境单 IP 注册限制和注册限流。

## 方案选择

采用“用户邀请码 + 邀请关系表 + 积分流水”的方案。

在 `users` 上直接保存固定邀请码，便于生成链接和按邀请码定位邀请人；使用独立关系表保存邀请历史、实际奖励金额和用户名快照；使用现有 `credit_transactions` 记录积分变动。相比把所有关系字段塞进 `users`，该边界更适合审计、删除账号后的历史展示和未来统计。

## 数据模型

### `users`

新增 `invite_code text`，普通用户唯一且非空，管理员为 `NULL`。迁移时为已有普通用户补齐随机邀请码，并建立唯一索引。新用户注册时生成加密随机的 URL-safe 字符串，遇到唯一冲突重试。

邀请码不使用用户 ID、用户名或递增序号，避免暴露内部信息和被枚举。生成后不提供修改或重新生成接口。

### `site_settings`

新增单行站点配置：

- `invitation_enabled integer not null default 1`：1 开启，0 关闭。
- `invitation_reward integer not null default 200`：非负整数，单位为积分。

管理员更新时校验布尔值和非负整数；数据库约束也保证奖励不会为负数。

### `user_invitations`

新增邀请关系表：

- `id uuid primary key`
- `inviter_id uuid references users(id) on delete set null`
- `invitee_id uuid references users(id) on delete set null`
- `inviter_username text not null`：邀请人用户名快照
- `invitee_username text not null`：被邀请人用户名快照
- `reward_amount integer not null`：本次实际采用的奖励值
- `created_at timestamp default now()`

对 `invitee_id` 建唯一索引，保证一个被邀请人最多绑定一个邀请人。两个用户外键都允许置空，使账号删除后关系历史仍然保留；展示历史时优先使用快照，当前账号状态通过可用的外键关联判断。

### `credit_transactions`

扩展流水类型 `invite_reward`。邀请奖励流水的 `amount` 为正数，`balance_after` 保存发奖后的余额，备注包含被邀请用户名。奖励为 0 时不写入积分流水，但关系表的 `reward_amount` 仍记录为 0。

## 注册与奖励数据流

邀请链接格式为当前站点域名的登录页地址：

```text
https://<site-origin>/login?invite=<invite-code>
```

注册页从 URL 读取邀请码，并在页面刷新、登录/注册切换时保留；注册请求把邀请码作为可选字段发送给现有注册接口。

注册处理顺序：

1. 执行现有注册限流，并检查站点注册开关。
2. 校验用户名、密码和注册 IP。
3. 如果邀请功能关闭，忽略邀请码，按普通注册继续。
4. 如果邀请功能开启且传入邀请码，查找邀请码对应的普通用户；邀请人必须为 `role=user` 且 `status=active`。不存在、管理员邀请码、已封禁邀请码统一返回邀请链接无效。
5. 在一个数据库事务中完成注册 IP 占位、创建用户并生成邀请码、写入新用户注册赠送流水、写入邀请关系、增加邀请人余额、写入邀请奖励流水。
6. 事务成功后签发登录 Cookie；任一步骤失败则回滚用户、关系、积分和注册 IP 占位。

数据库唯一约束和原子余额更新共同防止并发注册重复奖励。邀请关系只在被邀请账号成功创建后写入，因此用户名冲突、密码校验失败或数据库失败都不会产生奖励。

## 接口

### 用户端

- `GET /api/user/invitations`：当前普通用户的邀请码、成功邀请人数、累计奖励和邀请记录；管理员返回无参与资格状态。
- 现有 `POST /api/auth/register`：增加可选 `inviteCode` 字段，兼容没有邀请码的普通注册。

### 管理端

- 扩展现有 `GET /api/admin/site-settings`：返回邀请开关和奖励配置。
- 扩展现有 `PUT /api/admin/site-settings`：更新邀请开关和奖励配置。
- `GET /api/admin/invitations`：返回邀请记录、邀请人/被邀请人状态和汇总统计，使用现有管理员鉴权。

所有用户接口只返回当前用户数据；管理员接口使用 `requireActiveAdmin`，不接受普通用户传入的 user ID 来越权查询。

## 用户界面

### 钱包弹窗

在现有“我的钱包”中增加邀请区域，包含固定链接、复制按钮、成功邀请数、累计奖励和被邀请用户名/注册时间列表。邀请关闭时显示功能暂时关闭状态，不影响积分流水和其他钱包功能。

### 管理端

在现有“站点设置”增加邀请开关和奖励积分输入。在管理端增加邀请记录列表和统计区域，展示邀请人、被邀请人、实际奖励、注册时间及当前状态；删除账号的历史记录仍通过快照展示。

## 错误处理与安全边界

- 邀请功能关闭不会关闭普通注册。
- 邀请功能开启但邀请码无效时，返回明确错误；用户移除邀请码后仍可正常注册。
- 不信任客户端提交的奖励值、邀请人 ID 或用户名，所有信息由服务端根据邀请码和数据库配置决定。
- 奖励金额在事务中读取并保存到关系记录，之后管理员修改配置不会改变历史奖励。
- 不允许管理员账号作为邀请人；被封禁账号的链接不能用于新奖励。
- 不新增公开的全量邀请关系接口，不向非关联用户暴露关系数据。

## 测试与验收

### 服务端

- 新普通用户获得固定邀请码，管理员不获得邀请码。
- 现有普通用户迁移后都有邀请码且没有重复。
- 有效邀请码注册后邀请人余额增加 200，邀请关系和 `invite_reward` 流水同时存在。
- 奖励修改只影响之后的注册；奖励为 0 时只建立关系。
- 邀请关闭、邀请码无效、邀请人封禁时分别符合既定行为。
- 重复注册、并发注册、用户名冲突和注册事务失败均不会重复发奖或遗留 IP 占位。
- 普通用户无法查询他人的邀请数据，管理员统计与明细一致。

### 客户端

- 邀请链接打开后邀请码在刷新和注册/登录切换中不丢失。
- 钱包中可以复制链接并看到实时邀请数据。
- 邀请关闭和空记录状态展示清晰。
- 积分流水新增邀请奖励标签，既有流水展示不回归。

## 范围外

- 不做多级邀请、邀请排行榜、邀请奖励上限、邀请奖励人工撤销。
- 不增加邮箱/手机号验证；本期沿用用户名密码注册和现有单 IP 限制。
- 不改变现有注册赠送、签到、消费和管理员手动调整积分规则。
